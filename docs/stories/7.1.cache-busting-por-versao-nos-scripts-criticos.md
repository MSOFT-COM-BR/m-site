# Story 7.1: Cache-busting por versao nos scripts criticos do shell

## Story

- **Como:** usuario acessando mirandasoft.com.br apos um deploy.
- **Quero:** que o navegador/CDN sempre busquem a versao atual de `config.js` e dos demais scripts do shell.
- **Para que:** uma rota nova (ex: `/ecossistema`) ou qualquer mudanca de configuracao nao fique invisivel para quem tem uma copia em cache, sem depender de purge manual de CDN.

## Contexto (causa raiz confirmada)

`https://mirandasoft.com.br/ecossistema` retornava 404 mesmo com `ecossistema.html` existindo e servindo 200 no servidor, e mesmo `'ecossistema'` estando presente em `validPages` no `origin/master` do `config.js`. Investigacao:

- O roteador da SPA (`src/core/core.js:182`) rejeita qualquer `pageName` que nao esteja em `config.routes.validPages` (lido de `config.js`), lancando erro que cai no 404 interno.
- `curl -sI https://mirandasoft.com.br/src/config/config.js` mostrava `last-modified: Mon, 20 Apr 2026` e `cf-cache-status: HIT` — uma copia de tres meses atras, sem `'ecossistema'` na lista.
- `curl` com `?cachebust=<timestamp>` no mesmo arquivo forcou o Cloudflare a buscar do zero e retornou a versao correta, com `last-modified` de hoje e `'ecossistema'` presente — confirmando que **o servidor de origem esta correto**, e o problema e puramente cache do Cloudflare servindo uma URL antiga.
- `serve.json:40-46` define `Cache-Control: public, max-age=604800` (7 dias) para `/src/config/`, mas a resposta real via Cloudflare mostrava `max-age=14400` (4h) — confirma que o Cloudflare aplica seu proprio TTL/regra de cache por cima do header de origem, e nao invalida a URL automaticamente quando o arquivo muda no deploy.

**Resultado pratico:** qualquer mudanca em `config.js` (nova rota valida, nova config de API, etc.) pode ficar invisivel para uma fatia dos visitantes por ate o TTL do Cloudflare, apos cada deploy, sem nenhum sinal de erro no processo de deploy em si.

## Acceptance Criteria

1. `index.html` referencia `config.js` (e os demais scripts criticos do shell: `core.js`, `component.js`, `i18n.js`, `helpers.js`, `skeleton.js`) com uma query string de versao (`?v=X.Y.Z`), derivada de uma unica fonte de verdade.
2. A versao usada na query string e a mesma exibida no comentario `<!-- Version: VX.Y.Z -->` no topo do `index.html` — as duas nunca ficam dessincronizadas (hoje `index.html` mostra `V0.11.55` enquanto `config.js`'s `app.version` mostra `0.10.44`; esta story tambem corrige essa divergencia).
3. Um bump de versao (`index.html`'s comentario + `config.js`'s `app.version` + as query strings) e obrigatorio a cada deploy que altera `config.js` ou os arquivos `core/*` — documentado no fluxo de release do projeto (`AGENTS.md` ou README, onde já existir orientação de versionamento).
4. Alterar a query string invalida qualquer cache intermediario (CDN, navegador) para aquele arquivo especifico, sem precisar de purge manual.
5. Nao adiciona nenhuma etapa de build — o projeto continua sendo servido estatico via `serve`, sem bundler. A troca de versao e uma edicao de texto simples nos `<script src>`.

## Tasks

- [x] Unificar a fonte de verdade da versão: `config.js`'s `app.version` bumped para `0.11.56` (era `0.10.44`, divergente do comentário `V0.11.55` do `index.html`), e o comentário de `index.html` sincronizado para `V0.11.56`.
- [x] Adicionar `?v=0.11.56` em `index.html` nos `<script src>` de `config.js`, `component.js`, `i18n.js`, `helpers.js`, `skeleton.js`, `core.js`.
- [x] Documentar em `README.md` (seção "Desenvolvimento") que subir a versão nos três lugares é obrigatório ao mudar `config.js`/`core/*`, explicando a causa raiz do bug de `/ecossistema` como motivação.
- [x] Validado localmente: servindo com `npx serve -s .` (mesmo flag do `Dockerfile` de produção), o shell carrega `config.js?v=0.11.56` e o conteúdo do arquivo (via curl com a query string) contém `'ecossistema'` em `validPages`.

## Definition of Done

- [x] `config.js` e os módulos de `core/` carregam com `?v=` na URL.
- [x] Comentário de versão em `index.html` e `app.version` em `config.js` sempre iguais (ambos `0.11.56`).
- [x] Processo de deploy documentado para lembrar do bump de versão.

## Validation

- `node -e "new Function(...)"` não se aplica (mudança é só em tags `<script src>`/HTML, sem JS novo); verificação manual de que os 6 `<script src>` críticos têm `?v=0.11.56` bem formado (`python3 -c "re.findall(r'<script[^>]*>', ...)"`).
- Servido localmente com `npx serve -s . -l 8083` (mesma flag `-s` do `Dockerfile` de produção, garantindo fallback de SPA):
  - `GET /` retorna o shell com `config.js?v=0.11.56` no HTML.
  - `GET /ecossistema` (rota da SPA) retorna o mesmo shell (fallback funcionando).
  - `GET /src/config/config.js?v=0.11.56` retorna o arquivo real, contendo `'ecossistema'` em `validPages` — confirma que a query string não quebra a resolução do arquivo no static server (comportamento padrão: servidores de arquivo estático ignoram query string na resolução de path).
- Não validado nesta sessão: efeito real em produção (exige o deploy + observar se o Cloudflare busca a nova URL vs. serve a antiga). Isso só pode ser confirmado após o deploy desta mudança.

## Nota operacional

Além desta mudança de código, recomenda-se um **purge de cache no Cloudflare** (painel do domínio `mirandasoft.com.br`) logo após o deploy desta story, para eliminar imediatamente a cópia antiga de `config.js` que já está cacheada — sem isso, quem já tem a URL antiga em cache do navegador ou pegou a versão do Cloudflare antes do purge continua vendo 404 até expirar por conta própria.
