# Story 3.1: Criar usuario com acesso por aplicacao

## Story

- **Como:** Admin Master da Miranda Soft.
- **Quero:** criar uma conta para uma aplicacao especifica pelo painel administrativo.
- **Para que:** a pessoa receba somente a permissao necessaria, sem ganhar privilegios globais.

## Acceptance Criteria

1. O Admin Master visualiza uma aba de Usuarios no `/admin`, com nome, e-mail, senha, chave da aplicacao e nivel `viewer`, `editor` ou `owner`.
2. O formulario envia somente `POST /auth/admin/users`; ele nao permite escolher nem envia papeis globais.
3. O backend aceita a operacao somente para uma sessao ativa com o papel global `admin`, valida a versao do token no banco e rejeita usuario comum com `403`.
4. A conta criada recebe obrigatoriamente `roles: ['user']`, senha com hash Argon2 e um unico registro `mAppAccess` para a chave e nivel escolhidos.
5. Tentativas com e-mail ja usado retornam conflito sem criar acesso parcial; falhas ao conceder acesso removem a conta recem-criada.
6. O cadastro publico nao aceita mais `role` ou `roles` como fonte de privilegios e nao concede acesso automatico a uma aplicacao.
7. A criacao e registrada em auditoria sem incluir senha, e a lista de chaves de aplicacao conhecidas pode ser carregada pelo painel.

## Technical Contract

`POST /auth/admin/users`

```json
{
  "name": "Pessoa Exemplo",
  "email": "pessoa@empresa.com",
  "password": "senha-com-pelo-menos-12",
  "appKey": "bva",
  "appRole": "editor"
}
```

Resposta bem-sucedida: `201`, com a conta sem senha e o acesso criado. O endpoint nao emite token para a nova conta.

## Validation

- `bun test tests/auth.test.ts` com MongoDB descartavel: 11 testes, 41 assercoes aprovadas. Cobre cadastro publico com papel malicioso, ausencia de sessao, usuario comum, Admin Master, conflito de e-mail, listagem administrativa e token administrativo revogado.
- A suite completa `bun test` executou 24 testes: os 11 de autenticacao passaram; 13 falhas preexistentes em `blogs`, `tasks`, `healthtech` e `credentials` enviam requisicoes sem Bearer token para rotas que ja exigem autenticacao. Elas nao exercitam nem alteram este fluxo.
- `bun run build` do `m-manage` aprovado.
- `bunx tsc --noEmit --skipLibCheck` nao reportou erros nos arquivos modificados. O typecheck completo do repositorio ainda apresenta conflitos preexistentes entre definicoes de `bun-types` e dependencias.
- Smoke test do m-site com `serve -s`: HTTP 200 para `/`, `/admin`, `src/pages/admin.html` e `src/components/header.html`; a pagina entregue contem a aba e o contrato novos.
- `git diff --check` aprovado nos dois repositorios.

## Risk Follow-up

- Auditar em producao contas criadas antes desta entrega: o cadastro publico anterior aceitava `role` e `roles`, portanto podem existir contas com privilegio global indevido. Esta entrega impede novas escaladas, mas nao altera registros historicos automaticamente.
