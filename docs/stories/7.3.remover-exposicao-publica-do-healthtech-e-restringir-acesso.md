# Story 7.3: Remover exposição pública do HealthTech e restringir acesso por app instalado

## Story

- **Como:** Admin Master da Miranda Soft.
- **Quero:** que o HealthTech (dados de pacientes/prontuário) não seja anunciado numa página pública nem acessível a qualquer conta logada.
- **Para que:** área restrita de saúde (dado sensível/LGPD) não fique exposta a quem não deveria ter acesso.

## Contexto (dois problemas encontrados)

**1. Link público para área restrita.** `src/pages/ecossistema.html` (página pública, sem guard de autenticação) tinha um card "Healthtech" na seção "Rotas em destaque" apontando direto para `/healthtech-dashboard` — um convite explícito, para qualquer visitante anônimo, a entrar numa área que deveria ser restrita a quem tem o app instalado.

**2. Gate de acesso insuficiente no backend.** Investigando o motivo de o link "funcionar" (carregar dados de verdade em vez de dar erro), encontrei que `m-manage/src/routes/healthtech.ts:25-29` só exigia **sessão válida com qualquer conta** (`requireAuth`), sem checar se o usuário tinha o app `healthtech_os_v1` instalado (`mApps`) ou papel de acesso (`mAppAccess`). O próprio código já tinha um comentário `TODO` reconhecendo isso: *"isolar por pharmacyId/tenant via requireAppAccess quando o appKey do healthtech for registrado... hoje só bloqueia acesso totalmente anônimo."* Ou seja: **qualquer usuário cadastrado no site — grátis, premium, qualquer um — conseguia ler/escrever dados de pacientes, fórmulas e prontuários**, mesmo sem esse app fazer parte da sua conta.

Isso é mais sério que uma falha de UX: dado de paciente é dado sensível (LGPD). Remover só o link público não seria suficiente — qualquer pessoa que soubesse a URL `/healthtech-dashboard` (ou tivesse visto o link antes de removido) continuaria com acesso completo aos dados enquanto tivesse qualquer conta.

## Acceptance Criteria

1. `/ecossistema` não contém nenhum link para `/healthtech-dashboard` ou qualquer rota do módulo HealthTech.
2. `GET/POST/PUT/DELETE /healthtech/*` no backend exige, além de sessão ativa, que o usuário tenha `healthtech_os_v1` instalado (`mApps`, `status: 'active'`) — ou seja Admin Master.
3. Usuário autenticado sem o app instalado recebe `403` (não `401`, que já indicava "sem sessão" — a distinção importa para diferenciar "não logado" de "logado mas sem acesso a este app específico").
4. Admin Master continua com acesso total, independente de ter o app instalado na própria conta (mesmo padrão já usado em `GET /apps?all=1`).
5. `/premium`, que já só mostra o card do HealthTech para quem tem o app instalado (`APP_OVERRIDES`/`GET /apps`), continua funcionando sem alteração — o gate novo é no backend, não muda a experiência de quem já tinha acesso legítimo.

## Technical Contract

Nenhum endpoint novo. Mudança é na camada de autorização de endpoints já existentes:

| Method | Endpoint(s) | Mudança |
| --- | --- | --- |
| `*` | `/healthtech/*` | Gate trocado de `requireAuth` (sessão válida) para `requireAppAccess('healthtech_os_v1')` (sessão válida + app instalado, ou Admin Master). |

Nova função reutilizável em `m-manage/src/middleware/requireAuth.ts`: `requireAppAccess(appKey)`, para ser reaproveitada por outros módulos com o mesmo problema (nenhum outro módulo foi auditado nesta story — ver Riscos).

## Definition of Done

- [x] `/ecossistema` sem nenhum link para área restrita do HealthTech.

- [x] Cobertura de teste para os 4 cenários de autorização.

## Riscos / Fora do escopo

Esta story só cobre o módulo HealthTech, que foi o caso concreto reportado. **Não foi feita uma auditoria de todos os outros módulos do `m-manage`** para ver se o mesmo padrão de gate insuficiente (`requireAuth` genérico em vez de `requireAppAccess` por módulo) se repete em outro lugar (ex: `credentials.ts`/mcredential, `blogs.ts`, etc.). Recomenda-se uma auditoria dedicada como story futura, usando `requireAppAccess` (já criado aqui) como padrão a aplicar.
