# Story 7.2: Perfil do usuario real e dinamico

## Story

- **Como:** usuario autenticado do Miranda Soft.
- **Quero:** que `/profile` mostre meus dados reais e que salvar alteracoes realmente persista no backend.
- **Para que:** eu confie no que o painel mostra e consiga de fato mudar meu nome/senha, em vez de ver numeros inventados e um botao "Salvar" que so grava no localStorage do navegador atual.

## Contexto (mocks confirmados)

`src/pages/profile.html` tem os seguintes problemas:

1. **Card "Uso da Conta" (linhas 113-148):** "Apps Instalados 3/10", "Armazenamento 45%", "Chamadas API 1.2k/5k" — todos hardcoded no HTML, nao vem de nenhum dado real. O numero de apps instalados **existe** de verdade via `GET /apps` (ja usado em `premium.html`), mas nao e usado aqui.
2. **Card "Plano Premium" (linhas 90-111):** "Renovação: 18/02/2026" — mesma data fake ja removida de `premium.html` na story 5.2; aqui ainda esta presente.
3. **Formulario "Meus Dados" (linhas 154-224):** o submit do form roda um `setTimeout` de 1s simulando uma chamada de API (linha 207) e so grava o objeto atualizado em `localStorage` (linha 210). **Nao existe nenhuma chamada a `window.core.fetchAPI`.** Isso inclui a troca de senha: os campos existem no formulario, sao validados (senha == confirmacao), mas o valor da senha nunca e enviado a lugar nenhum — e descartado.
4. **Backend:** `GET /auth/me` existe e retorna o usuario real (`m-manage/src/routes/auth.ts:889`), mas **nao existe nenhum endpoint de auto-atualizacao** (`PUT /auth/me` ou equivalente). O unico jeito de mudar nome/senha hoje e via `PUT /auth/admin/users/:id`, que exige ser Admin Master **e** bloqueia explicitamente a auto-gestao (`findManagedUser` recusa `user.id === admin.sub`) — ou seja, nem um Admin Master consegue editar o proprio perfil por ali. Um usuario comum simplesmente nao tem como.
5. **Campo `bio`:** o form le/escreve `user.bio`, mas o schema `mAuth` (`m-manage/src/models/mAuth.ts`) nao declara esse campo. Como o schema usa `strict: false`, gravar funcionaria se houvesse uma rota real, mas hoje e so um campo fantasma que so existe no `localStorage`.

## Acceptance Criteria

1. Existe um endpoint de auto-atualizacao (`PUT /auth/me`) que aceita `name`, `password` (opcional) e persiste no `mAuth` do proprio usuario autenticado — sem exigir papel admin, sem aceitar mudanca de `roles`/`status`/`email` (mesmo padrao de allowlist estrita ja usado em `adminUserUpdateBody`).
2. O formulario em `/profile` chama esse endpoint de verdade via `window.core.fetchAPI`, com estado de loading/erro real (sem `setTimeout` simulando sucesso).
3. Trocar a senha pelo formulario realmente atualiza a senha no backend (hash `argon2id`, mesmo padrao do resto do sistema) e invalida a sessao atual apos a troca (forca novo login, mesmo comportamento ja usado em `updateManagedUser`).
4. O card "Uso da Conta" mostra o numero real de apps instalados (via `GET /apps`, ja usado em `premium.html`). As metricas sem fonte de dado real hoje ("Armazenamento", "Chamadas API") sao removidas — nao substituidas por outro numero inventado.
5. O card "Plano Premium" remove a data de renovacao fixa; mostra so o que e real (status do papel do usuario: premium/admin/user).
6. O campo `bio` e removido do formulario (nao existe no schema, nao ha requisito de produto para ele) — ou, alternativamente, adicionado formalmente ao schema `mAuth` e a rota `PUT /auth/me`, se o usuario confirmar que quer esse campo. Por padrao desta story: remover.

## Technical Contract

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `PUT` | `/auth/me` | Atualizar nome e/ou senha do proprio usuario autenticado. Novo endpoint. |
| `GET` | `/auth/me` | Ja existe — usar para popular o formulario ao carregar a pagina (hoje `profile.html` usa so o que esta em `localStorage`, que pode estar desatualizado). |
| `GET` | `/apps` | Ja existe (story 5.1) — usar para o card "Uso da Conta". |

  - `GET /auth/me` retorna o usuário real.
  - `PUT /auth/me` com `{ name }` renomeia com sucesso e a sessão continua válida (sem re-login necessário).
  - `PUT /auth/me` com `{ password }` retorna sucesso, invalida a sessão atual (`GET /auth/me` com o token antigo passa a retornar erro de autenticação), e login com a senha nova funciona.
  - Tentativa de `PUT /auth/me` com `{ roles: ["admin"] }` é rejeitada pelo schema (não persiste a escalação).

## Achado colateral (fora do escopo desta story)

Durante a validação manual contra `src/index.ts` (o entrypoint real de produção), a rejeição de payload inválido retornou **422** com o corpo de erro bruto do Elysia, não os **400** com `{ success: false, error: ... }` que os testes automatizados verificam. Investigação: `src/app.ts` tem um `.onError` global que normaliza erros de `VALIDATION` para 400 com corpo limpo — mas esse arquivo só é usado pelos testes (`tests/*.test.ts` importam `app` de `../src/app`). O `src/index.ts`, que é o arquivo realmente executado em produção (`bun src/index.ts`, ver `package.json`'s `start`), monta sua **própria instância `Elysia()`** do zero e nunca importa/usa `app.ts` — logo nunca herda esse tratamento de erro. Isso significa que **todo** erro de validação em produção (não só desta story) retorna o formato verboso do Elysia em vez do formato limpo esperado pelo frontend. O frontend desta story já trata isso de forma resiliente (mensagem genérica de erro), mas o formato de resposta em si está inconsistente com o que os testes garantem. Recomenda-se abrir uma story separada para unificar `index.ts` e `app.ts` em uma única definição de app, para que o que os testes validam seja de fato o que roda em produção.
